# Move Health onto its own Turso WAL file

## Outcome

Health stores its tables in its own Turso WAL file, like the owners listed in
[Split capability databases](storage-files.md), and no longer writes to the shared database.

## Acceptance

- `crates/health` opens its owner file through `crates/sjel-native-wal`, and the service builds
  with `turso-wal`.
- A receipt-backed shared-store restore supplies the export. The owner file matches both
  Health tables row for row.
- The first scheduled backup of the owner file restores with exact row parity.
- `GET /ready`, `health metrics` and `health summary` pass against the live owner.

## Evidence

Health was added with two tables in the shared database (`crates/health/src/store.rs`).

A `turso-wal` build keeps both tables in `data/health/health.db` in the overlay, with
`SJEL_HEALTH_DB_PATH` as an explicit override. The default `libsql` build still uses the
shared database, so the live service keeps that database until cutover.
Under `turso-wal`, `health import`, `metrics`, `imports` and `summary` send jobs to the owner
socket, and `health snapshot` requests a backup snapshot. `tools/backup.sh` registers the owner,
and `services/health-wal-backup` declares the backup unit.

The Health tests pass on both engines: 12 with `libsql`, 14 with `turso-wal`, including job
mapping and the refusal of a metric outside the catalogue. Clippy passes on both engines.
[`health-owner-rehearsal.sh`](../../research/benchmarks/storage-engine/health-owner-rehearsal.sh)
served a scratch owner file and imported a synthetic export through the CLI and the owner
socket. It read the values back without opening the shared database. An owner-snapshot backup
then restored three daily values and one import in isolation using the registered backup contract.
[`owner-store-split.py`](../../tools/owner-store-split.py) staged both tables from the restored
fixture with exact row parity and preserved the import sequence.

## Cutover and recovery

Run the [owner cutover command](../../tools/owner-store-cutover.py) from a regular deployment
operator terminal. The agent shell cannot open the live shared database.

```sh
python3 tools/owner-store-cutover.py health --check
python3 tools/owner-store-cutover.py health --apply
```

The preflight checks the running legacy process's launch settings, owner credentials and local
backup targets. libSQL closes database connections between requests, so an idle legacy process
need not have the database open. The native owner check verifies the open file.
Pause manual Health imports and other Health builds during apply. The command builds the
release candidate in a temporary target outside the checkout before maintenance. It then
holds Health, restores a fresh shared backup with its receipt, and checks the staged file
against the live Health rows. It then publishes the owner file, switches the tracked Health
build and resumes the service. It checks the API and CLI, restores an owner backup, and enables
`health-wal-backup`. Both restores use new, disposable destinations under overlay
`data/.restore-scratch`, inside the agent file wall but separate from live capability paths.
The command removes those extracted copies and does not delete the shared file, prune archives
or change agent access.

A failure before activation resumes the legacy build if the service files are unchanged or
can be restored. After activation, never switch back automatically; the new file may contain
writes. Repair and resume the owner if necessary, then run
`python3 tools/owner-store-cutover.py health --verify`. After an unhandled interruption, check
the maintenance hold, build declaration and deployed binary before resuming.

The restore test matrix verifies that regular restores reject overlay destinations and that
private scratch refuses live paths, symlink escapes, existing targets and agent sessions. The
synthetic Health rehearsal tested both receipt-backed restores, exact Health row and sequence
parity, and scratch cleanup. Eight cutover tests passed, including shared-restore failure before
activation.

The live cutover restored the shared backup, verified both Health tables and the import
sequence, and resumed Health on Turso WAL. Readiness, CLI metrics and summary, and the first
owner backup restore passed. Read-only MCP verified the preserved HealthKit import and new
signed uploads from the paired iPhone after cutover. The backup ledger records a successful
timer run after cutover. The scheduled archive has not yet been restored.

## Agent reads

The Health data ruling admits C1 reads for reviewed OpenAI and Anthropic providers. Both
providers resolve to the trusted ring. The owner set Health to `read-only` in Systems, and
Health was enabled in the deployment registry without restarting the service. Pi and Claude
Code each discovered four Health read tools and no write tools under their registered agent
identities. Both read live metrics through MCP, and the Health gate returned HTTP 403 to
both identities on the upload route. The reloaded Pi session discovers all four tools and
reads live metrics. This does not grant file access or unblock the storage cutover.
