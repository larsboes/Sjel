# Restore MCP discovery after retired capabilities

## Outcome

MCP discovers available capability tools inside the trusted harness profile and preserves
registry failures instead of reporting an empty-input JSON error.

## Acceptance

- Retired capabilities do not prevent the active machine registry from resolving.
- Failed registry subprocesses report their status and stderr before JSON parsing.
- Denied discovery metadata is reported, not treated as missing with an empty tool list.
- Trusted harnesses can read agent modes and gate manifests, but cannot write them or read
  adjacent personal data, overlay secrets or protected home credentials.
- A fresh normally contained Pi process connects and lists live tools.

## Implementation and verification

The stale enabled web-links entry was removed with `tools/capability.sh disable web-links`.
The capability was retired in source; no service or stored data was deleted in this repair.
`pi mcp list` subsequently connected, but returned zero tools inside the existing sandbox.

The MCP server now checks registry subprocess status and retains its stderr. Discovery uses
`try_exists` to distinguish denied metadata from missing metadata. The trusted profile exempts
only reads of `data/agent-modes.json` and `data/agent-gates/`; all data writes remain denied.
Tests cover registry output and profile rendering; the native acceptance test checks readable
metadata, denied writes and continued denial of private data and credentials.

The MCP suite passed 25 tests before the later `try_exists` change. The containment native test
compiled, but could not apply a nested sandbox: `sandbox-exec: sandbox_apply: Operation not
permitted`. Later locked test reruns were blocked by concurrent workspace manifest/lockfile
inconsistency. No lockfile repair was attempted. Final source changes require rerunning the
focused suites. The profile has not been deployed or accepted in a fresh Pi process.

## Permission scope

The operator approved a narrow MCP access repair and a review of broader private-overlay
configuration access. No blanket overlay grant or command-policy removal was approved or
implemented. OS containment already admits ordinary configuration reads; the command-policy
protected overlay root still gates writes. A broader routine configuration-write grant needs
an explicit boundary that excludes secrets, provider/agent policy and executable hooks.
