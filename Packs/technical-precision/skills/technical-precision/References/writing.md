# Technical Writing, Procedures, Quantities, and Requirements

## Technical prose

- Lead with the central claim, decision, or purpose.
- Prefer active voice when the actor matters.
- Put one idea or instruction in each sentence when practical.
- Prefer direct verbs over nominalizations.
- Use one stable term per concept.
- Keep subjects, actors, conditions, units, versions, and qualifiers explicit when material.
- Prefer short sentences without deleting precision.
- Avoid semicolons and dense clause chains when separate sentences are clearer.
- Use lists for sequences or complex conditions.
- Keep one topic per paragraph.
- Delete marketing adjectives unless evidence/measurement supports them.


## Procedures

- Number multi-step procedures.
- Put prerequisites before the step that needs them.
- Put one bounded action in each step.
- State exact commands, paths, versions, identifiers, units, and expected outputs where relevant.
- Put safety conditions before the action they constrain.
- Do not hide required behavior behind vague verbs such as "consider" or "try".


## Concepts and explanations

- Define only terms needed for the current question.
- Use one concrete example when it reduces ambiguity.
- Compare with the nearest confusable concept when that prevents misunderstanding.
- Do not add background merely because it is related.

## Calculations and quantitative claims

- State units for material inputs.
- Keep unit conversions explicit.
- Show a compact formula/derivation when the result is non-obvious or affects a decision.
- Use appropriate significant figures; avoid false precision.
- Distinguish measured, configured, estimated, and theoretical values.
- Check order of magnitude and boundary cases.
- State assumptions that materially affect the result.

## Requirements

Use normative language precisely:

- **MUST / MUST NOT:** absolute requirement/prohibition.
- **SHOULD / SHOULD NOT:** strong recommendation with possible valid exceptions.
- **MAY:** genuine option.

Do not use uppercase requirement words for emphasis. Do not upgrade recommended -> required, can -> will, normally -> always, or similar modality changes.

When interpreting another specification, preserve its definitions and normative vocabulary.
